The Problem
What is broken about how Bengaluru handles civic complaints today
Civic complaints are invisible individually, catastrophic collectively
The I Change My City (ICMC) platform receives thousands of road-related complaints from Bengaluru citizens every year — potholes, flooding, road resurfacing, broken footpaths. Each complaint is a data point. But no one is connecting the dots: a ward that generates 40 pothole complaints over four years with a 60% unresolved rate is structurally different from a ward that gets 5 complaints once. The current system treats every ticket the same.
No prioritisation signal
BBMP ward officials have no ranked view of which infrastructure problems are chronic vs one-off, which are getting worse, and which have been ignored the longest. Decisions are reactive, not data-driven.
No explainability
Even if a priority score existed, ward officials and journalists need to understand why — what drove the score, what the evidence is, what a reasonable next step would be. A number without context is not actionable.
Data is siloed
Complaint data (ICMC), work order spend (KAUN BBMP), and geographic ward boundaries exist in separate datasets with no common key. No one has joined them into a unified view.
The accessibility gap
Even when data is available, only someone with SQL or Python skills can query it. Ward officials, journalists, and RWA members cannot ask "what is the worst pothole ward in South Bengaluru?" and get a real answer.
The Solution: CivicLens
A three-layer AI system: data pipeline → interactive explorer → conversational analyst
Core insight: Bengaluru's civic problem is not a data shortage — it is a signal extraction and accessibility problem. CivicLens converts raw complaint noise into structured, ranked, explainable civic cases, then makes them queryable in plain English using RAG-grounded LLM reasoning.
Layer 1 — Data Pipeline (Python)
A fully automated Python pipeline ingests three data sources — 5,072 ICMC road complaints (2019–2022), KAUN BBMP work orders (2023–2026), and 243-ward GeoJSON boundaries — and produces 298 structured civic "cases." Each case is a cluster of related complaints: same ward, same problem category, recurring over time.

Clustering: Two strategies run in parallel. geo_dbscan groups complaints by GPS proximity (spatial clusters). ward_temporal groups by ward × complaint category × year (temporal patterns). Both are merged and deduplicated.

Ward enrichment: 206 wards matched exactly by name, 66 matched by fuzzy string similarity, 26 matched by GPS centroid proximity. Every case knows which ward it belongs to.

Priority scoring: Each case receives a 0–1 score from five weighted factors: complaint volume (30%), unresolved rate (25%), recurrence in years (20%), geographic spread (15%), re-open rate (10%). HIGH ≥ 0.5, MEDIUM 0.3–0.5, LOW < 0.3.
Layer 2 — CivicLens UI (React + Vite)
A single-page application with three views:

City Overview: KPI cards (298 cases, 48 HIGH, 194 MEDIUM, 56 LOW, 3,895 complaints, 86 wards affected). Line chart showing complaint activity year-on-year 2019–2022. Subcategory bar chart (57% pothole repairs, 34% road resurfacing). Top 15 worst wards by case count.

Ward Explorer: Leaflet.js interactive map of Bengaluru with proportional circle markers (size = complaint count, colour = priority tier). Filter by ward and priority. Click any marker → case preview in side panel. Click "Ask AI" → jumps to AI Chat with that case pre-loaded.

Case Registry: Searchable, sortable table of all 298 cases with inline tier badges, complaint counts, unresolved rates, and direct links to full case detail pages.
Layer 3 — AI Chat Assistant (RAG + LLM)
The AI assistant operates in two modes, automatically selected based on context:

Case mode (case selected): The full CaseFull record — priority factors, evidence items, work orders, hypotheses, rationale — is injected directly into the system prompt. The LLM can explain exactly why a case scored HIGH, what the evidence shows, and what a ward official should do next. No retrieval needed; the data is already there.

City mode (no case selected): Uses Retrieval-Augmented Generation (RAG). The user's question is embedded in-browser using all-MiniLM-L6-v2 running as a WASM module via @huggingface/transformers. The resulting 384-dim vector is compared via cosine similarity against 298 pre-computed case embeddings (built offline, served as a static JSON file). The top-5 most semantically relevant cases are fetched and injected into the system prompt. The LLM — Qwen 27B via Groq API — then answers with real ward names, real scores, and real complaint counts. No hallucination.

Widget generation: When the question is comparative ("which wards are worst?", "show me the tier breakdown"), the LLM can optionally emit a structured JSON chart spec that the UI renders inline as a bar, pie, or stat widget — no external charting library needed.
AI Architecture — How the Intelligence Works
The specific AI design decisions and why they were made
ICMC + KAUN + GeoJSON → Python Pipeline → 298 Scored Cases → Embeddings (build-time) → RAG (runtime) → Qwen 27B
DecisionWhat was chosenWhy
Embedding modelall-MiniLM-L6-v2 (384-dim)Runs in-browser via WASM — zero server infrastructure. Pre-compute once at build time; cosine search is instant at query time. Identical model for build and runtime ensures vector space consistency.
Vector storageStatic JSON file (2.3 MB)298 cases × 384 dims fits in a single served file. No vector DB (Pinecone, pgvector) needed. Loads once, cached in memory, O(n) cosine search is fast enough for 298 vectors.
LLMQwen 27B via GroqTested against available models on the account. Qwen 27B follows system prompt instructions cleanly, produces structured markdown, and optionally emits widget JSON. Reasoning models (gpt-oss) leaked chain-of-thought into responses — rejected.
Context strategyStructured case injection, not full-text retrievalCaseFull records are already structured (factors, evidence, rationale, work orders). Injecting them directly is more reliable than embedding case descriptions and doing fuzzy retrieval. RAG is used for routing/discovery; structured injection is used for depth.
Widget renderingLLM-emitted JSON → custom inline rendererThe LLM decides when a chart helps (comparative/quantitative queries). Emits a typed JSON spec; UI renders it as bar/pie/stat widget. No external charting library in the chat panel — pure CSS + SVG.
Scoring formulaWeighted linear combination of 5 signalsInterpretable, auditable, and tunable. Each factor maps to a real civic concept (volume, neglect, chronicity, spread, fix quality). No black-box ML — every score can be explained in plain English.

Technical Summary
Full stack overview
Data Pipeline
Python · Pandas · scikit-learn · DBSCAN · Fuzzy string matching · GeoPandas · JSON output
Frontend
React 18 · TypeScript · Vite · Tailwind CSS v4 · React Router · Recharts · Leaflet.js
AI / ML
@huggingface/transformers (WASM) · all-MiniLM-L6-v2 · Cosine similarity RAG · Qwen 27B · Groq API
Infrastructure
100% static — no backend server, no database, no auth. Served as a Vite SPA. All AI calls go directly from the browser to the Groq API.
What's Next
If this were taken beyond the hackathon POC
Live data feed: Connect to ICMC's live API so cases update automatically rather than being a 2022 snapshot.

Multilingual AI: The ward official audience in Bengaluru is Kannada-first. The AI assistant should respond in Kannada when asked.

Work order correlation: The temporal gap between ICMC complaints (2019–2022) and KAUN work orders (2023–2026) is currently flagged but not bridged. With better data, you could ask "did the ₹2.4Cr road work in Bellandur actually fix the pothole problem?"

Multi-city generalisation: The pipeline is city-agnostic. The same system could run on Chennai, Hyderabad, or Mumbai complaint data with minor config changes.

Offline mobile app: The RAG retrieval is fully client-side — it already works offline after first load. A PWA wrapper would make CivicLens usable by ward officials in areas with patchy connectivity.
